# H100: FastKernels and vLLM 0.18.0 versus 0.26.0

6 models passed, with 28 accepted workload comparisons; 3 models failed; 38 rows were skipped.

Hardware: one NVIDIA H100 SXM 80 GB. Diagnostic sweep selected from `full.yaml`; standard vLLM comparisons only, FastKernels included.

**Settings:** eight throughput requests per workload, one paired repeat, one full throughput warmup, three latency warmups and three measured latency iterations. Latency batch sizes are unchanged. This is a functional diagnostic, not the canonical-size paper experiment; one repeat cannot produce a repeat confidence interval or establish multi-GPU scheduling fairness.

**Provenance:** text-model results and Gemma/Jamba failures came from commit `9951fc6`. The first multimodal attempt exposed a missing source import path in the isolated reference environment. That run was interrupted and all four multimodal models were rerun at commit `98add81`, which fixes the import while preserving separate environment dependencies. Each reported old/new pair was produced entirely within its respective run.

Both versions use frozen inputs, identical request budgets and allocated GPUs. Values compare release environments, including their dependency differences. `FK / old run` and `FK / new run` are repeated measurements of the same FastKernels implementation.

## Command

After environment setup, the initial diagnostic used:

```bash
fastkernels validate drift 0.18.0 0.26.0 \
  --env-root /workspace/envs --output-dir /workspace/drift-results \
  --max-requests 8 --repeats 1 --latency-iters 3 --timeout 1200
```

The fixed multimodal rerun used the same settings with `--scenarios /workspace/multimodal.yaml` and a new output directory. That file selected the unchanged Whisper, Qwen2-VL, Qwen3-VL and Qwen2.5-Omni rows from `full.yaml`.
